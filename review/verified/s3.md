## 2. Details for changed findings

### FOUND-005 — S3 Bucket Keys apply to SSE-KMS only

**Change from triage:** Moved from UNVERIFIED to CONFIRMED (error), now with direct evidence.
**Original assessment:** ERROR, UNVERIFIED, MEDIUM. Bucket Keys likely apply to SSE-KMS only; only the DSSE-KMS exclusion had been checked.
**Verified conclusion:** The note's "Can be enabled for SSE-S3 and SSE-KMS" is wrong. Bucket Keys are an SSE-KMS feature only (not SSE-S3, not DSSE-KMS). The note's other bullets are correct: short-lived bucket-level key kept in S3, fewer KMS requests, unique key fetched per requester, configurable at bucket or object level. The bullet is also nested under Client-Side Encryption, but it concerns server-side encryption with KMS.
**Official evidence:** The Bucket Key page is titled "Reducing the cost of SSE-KMS with Amazon S3 Bucket Keys" and describes Bucket Keys only in terms of SSE-KMS ("S3 Bucket Keys for SSE-KMS"; "When you configure your bucket to use an S3 Bucket Key for SSE-KMS, AWS generates a short-lived bucket-level key from AWS KMS, then temporarily keeps it in S3"). It states "S3 Bucket Keys aren't supported for dual-layer server-side encryption with AWS KMS keys (DSSE-KMS)". It also says "Unique bucket-level keys are fetched at least once per requester". There is no mention of SSE-S3 support (SSE-S3 does not call KMS).
**Source:** Reducing the cost of SSE-KMS with Amazon S3 Bucket Keys — https://docs.aws.amazon.com/AmazonS3/latest/userguide/bucket-key.html (intro, "S3 Bucket Keys for SSE-KMS", "Configuring S3 Bucket Keys"); Using dual-layer server-side encryption with AWS KMS keys (DSSE-KMS) — https://docs.aws.amazon.com/AmazonS3/latest/userguide/UsingDSSEncryption.html ("S3 Bucket Keys aren't supported for DSSE-KMS").
**Recommended disposition:** CORRECT
**Proposed replacement:** Change "Can be enabled for SSE-S3 and SSE-KMS" to "Can be enabled for SSE-KMS only (reduces KMS request costs)", and move the S3 Bucket Key bullet group under SSE-KMS rather than Client-Side Encryption.
**Remaining uncertainty:** None material.

### FOUND-008 — Mountpoint "cannot delete files"

**Change from triage:** Moved from UNRESOLVED to CONFIRMED (ambiguity). The behaviour page that previously returned HTTP 504 is now readable.
**Original assessment:** AMBIGUOUS, UNRESOLVED, LOW. The user guide says Mountpoint cannot "delete directories", not files, and the behaviour page could not be fetched.
**Verified conclusion:** The note's "cannot … delete files" is only true by default. Mountpoint can delete files if started with `--allow-delete`. The user guide wording differs from the note ("delete directories"). The user guide and the semantics document are not perfectly aligned on directories (the semantics document says `rmdir` is supported for empty directories created by `mkdir`), so no directory claim is proposed.
**Official evidence:** The semantics document says "By default, Mountpoint does not allow deleting existing objects with commands like `rm`. To enable deletion, pass the `--allow-delete` flag", and that deletes immediately delete the object from S3. It also confirms no symbolic/hard links and no POSIX file locks. The user guide says Mountpoint "cannot modify existing files or delete directories, and it does not support symbolic links or file locking".
**Source:** Mountpoint for Amazon S3 file system behavior (AWS Labs / AWS-maintained repository, doc/SEMANTICS.md) — https://github.com/awslabs/mountpoint-s3/blob/main/doc/SEMANTICS.md (section "Deletes", "Overview"); Mount an Amazon S3 bucket as a local file system — https://docs.aws.amazon.com/AmazonS3/latest/userguide/mountpoint.html.
**Recommended disposition:** CLARIFY
**Proposed replacement:** "It **cannot** modify existing files or support symbolic links or file locking. Deleting files is off by default (can be enabled with `--allow-delete`)."
**Remaining uncertainty:** The behaviour source is the AWS Labs GitHub repository linked from the AWS docs, not a docs.aws.amazon.com page. Very low SAA relevance, so the edit is optional.
